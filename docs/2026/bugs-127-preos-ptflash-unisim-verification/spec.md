# Организация интерфейса к БД на основе CAS номеров компонентов

Имеются вспомогательные функции для формирования плана определения BIP компонентов смеси. В настоящее время функции работают только с формулами, хотя интерфейс БД, используемой для определения BIP, поддерживает получение свойств компонента как по формуле, так и по CAS. С точки зрения бизнес-логики CAS предпочтительнее, т.к. является уникальным для каждого компонента. При обмене списком компонентов между UI и расчетным модулем vlelib также используются CAS номера.

Предлагается выделить приватные методы `resolve_cas_number(component)` и `resolve_cas_numbers(component_list)` в `thermo_db_t`, которые выполняют конвертацию переданного списка компонентов в CAS формат по следующим правилам:
1. Изначально переданный компонент трактуется как CAS. Если переданный CAS не найден среди присутствующих в БД, то компонент считается заданным формулой.
2. Выполняется попытка получить CAS для формулы компонента. Если CAS не найден (или найдено более одного CAS), то формируется ошибка. Если найден единственный CAS, то заданная пользователем формула заменяется на этот CAS.

## Предлагаемая архитектура

Методы `resolve_cas_number` / `resolve_cas_numbers` — приватные в `thermo_db_t`: преобразование имен — внутренняя ответственность БД для поддержки инварианта интерфейса. Публичный `get_components` переводится на их использование, чтобы логика преобразования «CAS / формула» не дублировалась. Снаружи резолв доступен через `get_components` (далее `CASno` у свойств).

Хелперы формирования плана BIP (`generate_bip_estimation_plan_use_db_only`, `generate_bip_estimation_plan_with_correlation`) принимают тот же список идентификаторов, что и остальной интерфейс БД (формула или CAS), и внутри резолвят их через `get_components` глобальной `components_database`, затем строят пары CAS и записи плана. Отдельные перегрузки «только формулы» / «только CAS» не вводятся. Параметр локальной БД у хелперов не вводится: псевдокомпоненты и кастомные БД покрываются ручной сборкой плана.

Итоговая цепочка при создании флюида с планом BIP: список идентификаторов → `get_components` (`resolve_cas_number` / `resolve_cas_numbers`) → план с парами CAS → `estimate_bip_matrix` → матрица $k_{ij}$.

## Тесты

Уже есть: `BinaryCoefficientsPlan.BuildsDbOnlyPlanFromFormulasAndCas_ReturnsSameMatrix` (`testing/test_bips.h`) — одинаковый план `use_db_only` и матрица BIP для смеси, заданной формулами и CAS. `BinaryCoefficients.ThrowsIfFormulaIsDuplicated` — проверка целостности глобальной БД (отсутствие дублей формул), а не негативный сценарий резолва.

Добавить:
1. `get_components` для известного CAS и для известной однозначной формулы возвращает один и тот же компонент.
2. `get_components` для неизвестного идентификатора и для неоднозначной формулы (несколько CAS на тестовой/локальной БД) формирует ошибку.
3. `get_components` по списку формул и по списку CAS одной и той же смеси возвращает один и тот же набор свойств.
4. Аналог `BuildsDbOnlyPlanFromFormulasAndCas` для `generate_bip_estimation_plan_with_correlation` (одинаковый план и матрица при формулах и CAS).
